## 1. 用户目标与设计约定

用户希望减少文件覆盖组与主题 scope 的重复审查，同时保留双方独有的发现能力；任务清单和黑板必须让人能看见待办、进行中、结论和缺口。用户明确认为过度复杂的流程不可取。

采用：一个任务清单、一个共享黑板、两类 scope。复用现有服务和 Coordinator，不新增 AI 总管或独立调度服务。

- Coordinator 是已有 Python 类 `HarnessCoordinator`，负责实际调度、状态、预算与并发。
- Planner 是 AI，提出专题与计划调整；不能删除文件审查兜底。
- Discovery 是执行调查的 AI，需要边查边提交证据、候选与独立线索。
- 文件审查 scope：程序按完整文件清单分配，第一版继续每组 6 文件。
- 专题调查 scope：业务操作或资产 × 安全属性，如“文件下载 × 对象授权”。
- controller/service/mapper 是架构标签；SSRF/越权/注入是风险标签，不分别开组全仓重复扫。
- 验证和攻击路径是任务类型，不再建立额外 scope 家族。

重要：第一阶段只区分并展示任务类型；本轮接通增量线索的动态 Planner 最小闭环，但初始专题规划逻辑尚未完成改造。

- [x] 明确区分源码事实、模型假设和验证结论。
- [x] 增量候选与最终候选输出幂等合并，不重复建立验证任务。

子 agent 的决策边界：

| 遇到什么 | 怎么处理 |
| --- | --- |
| 回答当前问题需要跨文件追踪 | 自己继续，不请求重新规划 |
| 当前问题的新证据 | 立即发布，然后继续 |
| 有依据的候选漏洞 | 立即登记，进入验证待办，不必先找 Planner |
| 独立的新问题 | 发布新线索，当前 agent 继续原任务 |
| 当前问题预算内查不完 | 保存具体断点及已有证据，请求续查 |
| 工具失败或必要材料缺失 | 记录受阻原因及需要什么 |

禁止用“发现较大”或“跨了目录”作为必须重新规划的标准。子 agent 不得自行无限派生 agent。

### 4.2 线索收件箱

- [x] 扩展现有 CrossScopeLead：具体问题、起点、证据引用、来源任务、处理状态、关联任务、处理理由。
- [x] 修正 lead ID：身份包含具体问题和起点，同一对 scope 的不同问题分别保留。
- [x] Coordinator 接收新事件：普通证据直接更新；候选进入验证队列；精确重复线索关联原记录；需要规划的线索进入收件箱。
- [x] 同一任务补证或重试复用原任务并追加执行历史；独立新问题才创建新任务。
- [x] 收件箱持久化，重试/异常不能把未消费事件标为已处理。
- [x] 即便目标 scope 已完成，新线索也必须被接收和处理。

### 4.3 按缺口续跑

- [x] 未读区间 → 继续原文件审查。
- [x] 基础检查未完成 → 补具体检查。
- [x] 跨文件关系或控制条件未知 → 专题调查。
- [x] 候选无裁决 → 只补验证，不重跑 Discovery（若另有未读文件等发现缺口，仍可续查）。
- [x] 攻击路径不足 → 补攻击路径。
- [x] 工具失败 → 有界重试，失败后保留受阻。

以上已接入具体缺口记录和对应有界执行；模型未报告的业务检查缺口不会被程序凭空推断为已完成。

## 5. 动态 Planner：必须补全的时序约定

Planner 不常驻轮询、不每个工具调用都执行。Coordinator 管理事件和计时，按需要调用 Planner，Planner 可以与 Discovery 并行。

### 初始规划

- [x] 程序固定文件归属；Planner 根据架构、威胁模型、现有文件任务创建具体专题。
- [x] 每项专题要求问题、起始位置（源码文件）、原因、完成条件和优先级。
- [x] 超出本批调度上限的任务保留待办，不能按 `[:12]` 丢弃。
- [x] 明确本批任务数量、模型并发与总预算是不同限制（尚未实现全局费用预算）。
- [x] 保留主动主题探索，不能只调查文件组已经提出的候选。

### 再规划触发

- [x] 某项任务结束且收件箱有待处理事件：合并增量后调用 Planner。
- [x] 最老事件等待超过可配置窗口时触发（默认 60 秒）；与 Discovery 并行但仍受共享模型并发限制。已做无模型时序测试，尚未真实审计实测。
- [x] 有执行空位、没有可运行任务、但有待规划线索：立即规划。
- [x] 所有执行任务结束：检查是否还有未处理的已知缺口，必要时做最后一次规划。
- [x] 同时最多运行一个 Planner；普通触发可用最小调用间隔合并事件。
- [x] 新事件不能重置最老事件的等待计时，防止永远不触发。

### Planner 输入和输出

输入：任务目录与状态、上次之后的事件、相关证据、剩余预算。不要每次重新发送全部源码或全部历史。

输出只允许有边界的计划调整：新增独立任务、关联已有任务、补充证据、调整待办优先级、合并重复待办、记录不适用或延期原因。

- [x] 程序校验输出中的任务 ID、字段、状态迁移和预算；程序保证文件归属不被规划结果移除。
- [x] 使用事件序号/水位线记录此次输入，只确认处理该快照范围内的事件。
- [x] Planner 运行期间的新事件留在下一批，不一起清空。
- [x] Planner 失败或无法解析时保持收件箱，按有限重试处理。

### 运行中任务更新

- [x] 默认不中断正在执行的任务。
- [x] 更新写入任务待处理事项；agent 在关键追踪或结束前通过 BOARD 获取相关更新。
- [x] 第一版不做强行注入运行中提示词。
- [x] Coordinator 在任务完成时核对未消费更新；若还有必要事项，安排原任务续查。不能只依赖 agent 自觉读黑板。

### 停止条件

- [x] 正常收尾：已完成已知缺口尾扫；剩余受阻、延期或预算未处理项必须明确保留，不能称为全部完成。
- [x] 存在受阻/延期项时可以结束本次运行，但必须明确带未完成事项结束。
- [x] 设置总时间/模型预算、Planner 调用预算、单任务重试与无进展续查限制（预算执行边界见顶部）。
- [x] 仅换标题、无新问题/新证据的精确重复线索不得重新启动同一调查；不声称识别任意语义等价改写。
- [x] 最后检查只处理已知缺口，不无限要求模型再想几个问题。
- [x] 预算耗尽停止派发，保留所有剩余待办及停止原因。
