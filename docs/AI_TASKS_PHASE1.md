# 统一审计任务：第一阶段

后续任务与动态 Planner 时序约定见 [AI_AUDIT_NEXT_SESSION.md](AI_AUDIT_NEXT_SESSION.md)。第一阶段已于 2026-09-17 部署到本机 Docker 的 worker、gateway、frontend，均通过健康检查。

本阶段在现有 `Blackboard.work` 上扩展任务元数据和执行历史，没有建立第二份调度清单。

## 已接入

- 文件审查、专题调查、候选验证、攻击路径使用同一种任务记录。
- scope 任务在规划后发布，验证及攻击路径任务在各自阶段派发前登记。
- 状态包括待办、进行中、已完成、受阻、已取消，兼容旧 abandoned 数据。
- 一次重派发追加一次执行历史。批量模型调用关联多项任务，任务按各自结果结束。
- 验证与攻击路径任务按现有 `(file,line,type)` 聚合规则复用，关联全部候选实例。
- `work_item` 事件携带执行台账的快照，通过既有 `/v1/audit/{id}/trail` 增量接口传给前端。
- 前端提供类型/状态筛选、任务详情、文件读取进度、执行历史、关联候选及证据摘要。
- 共享黑板面板展示 agent 已发布的 record 摘要；不是完整源码黑板的另一个副本。
- 已读取文件数与任务完成状态分别显示。预算用尽但无可用输出不能满足覆盖检查。
- 取消运行时保存任务、黑板及报告，再把取消信号交回原作业系统。
- 运行结束保留未完成任务和原因，报告不再把“结束”统一描述为“收敛完成”。

## 兼容和边界

- 不改变现有 Planner 规划策略、scope 分类来源、轮次上限或验证规则。
- 文件审查与专题调查的完成状态仍基于现有覆盖闭合判定，尚未增加逐安全属性的检查台账。
- 不包含动态 Planner 收件箱、lead 自动派发、人工追加/单项重试。这些属于下一阶段的协作闭环。
- 运行取消沿用已有按钮；中途进程被强制杀死时前端保留最后事件，并提示运行已结束，不能推断任务完成。
- 旧运行没有 work_item 事件时显示兼容提示，原 agent、候选、覆盖和报告仍可查看。
- 前端展示的是事件投影；调度始终读取黑板中的 WorkItem，事件不会反向控制执行。
- 无新增 API 路径，无需变更前端 API 地址。上线需要更新执行审计的 Worker 和前端资源。

## 验证

使用脚本模型和本地数据验证任务重复领取、重试历史、同一 scope 下不同任务类型隔离、批次部分结果、候选实例聚合、取消持久化、预算无输出、事件 API 与前端乱序快照处理。浏览器使用合成任务数据检查列表、筛选和详情。未触发真实付费模型审计。
